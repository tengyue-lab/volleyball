# Volleyball App — Ranked Position Preferences & Matchmaking Algorithm Upgrade

You are working on an existing volleyball management application. **Do not rebuild the application or change unrelated functionality.** First inspect the existing codebase and understand how player profiles, positions, matchmaking/team balancing, ELO, match history, and the database currently work.

The goal of this task is to replace the current "select multiple positions" system with a **ranked position preference system**, and then update the matchmaking algorithm to use those rankings.

## 1. Player Position Preferences

Currently players can select multiple positions without ranking them.

Change this so each player has a **ranked list of preferred positions**.

The available positions are:

* Setter (S)
* Outside Hitter (OH)
* Middle Blocker (MB)
* Opposite (OPP)
* Libero (L)

### Requirements

* A player must select **at least 3 positions**.
* A player may select more than 3 positions.
* Each position can only appear once in a player's preference list.
* The player must be able to drag/reorder their selected positions.
* The order represents preference:

  * Rank 1 = strongest preference
  * Rank 2 = second preference
  * Rank 3 = third preference
  * etc.
* Players should not be required to rank positions they do not want to play.
* The UI should clearly communicate that the order matters for matchmaking.

Example:

Player A:

1. Setter
2. Opposite
3. Outside Hitter

Player B:

1. Outside Hitter
2. Middle Blocker
3. Opposite
4. Setter

Player C:

1. Middle Blocker
2. Outside Hitter
3. Opposite
4. Libero

The system must preserve this ranking in the database.

## 4. Matchmaking Algorithm

This is the most important part of the task.

The existing matchmaking algorithm currently uses whether a player can play a position, but the new algorithm must use the **ranked preference list**.

Do not simply convert the ranked list into a boolean "can/cannot play" system.

The ranking must materially affect the result.

### Core principle

The algorithm should prioritise giving players their highest-ranked available position while still producing valid teams.

For example:

Player A:

1. Setter
2. Outside
3. Opposite

Player B:

1. Outside
2. Setter
3. Opposite

If only one Setter position is available and one Outside position is available, the algorithm should strongly prefer:

Player A → Setter

Player B → Outside

rather than treating the two players as interchangeable.

### Position scarcity

The algorithm must also account for players who have fewer alternatives.

A player who has:

1. Setter
2. Outside
3. Opposite

should generally have higher priority for Setter than a player who has:

1. Setter
2. Outside
3. Middle
4. Opposite
5. Libero

because the second player has more alternatives.

Therefore the algorithm should consider both:

* Preference rank
* Number of alternative positions available to that player

This is important for avoiding situations where a flexible player takes a position that a specialist needs.

## 6. Team Assignment

The algorithm should optimise position assignment before ELO balancing.

Use the following priority order:

### Priority 1 — Validity

Every player must be assigned to a position that appears in their ranked preferences.

No player may be assigned to a position they did not select.

### Priority 2 — Position feasibility

Ensure both teams have the required positional composition.

### Priority 3 — Player preference

Among valid solutions, maximise player satisfaction by giving players higher-ranked positions.

A practical scoring system can be used, for example:

* Rank 1 = highest score
* Rank 2 = lower score
* Rank 3 = lower again
* etc.

However, do not blindly assume a particular scoring formula is optimal. Inspect the existing algorithm and choose a deterministic scoring method that properly rewards higher-ranked preferences.

### Priority 4 — Specialist protection

When two players compete for the same position, prefer the player for whom that position is more important and/or who has fewer viable alternatives.

Do not allow flexible players to systematically take positions away from specialists.

### Priority 5 — ELO balance

Only after finding strong valid positional assignments should the algorithm optimise team ELO balance.

ELO balancing must not override the fundamental positional requirements or cause players to receive positions they did not select.

## 7. ELO Balancer Button

Preserve the existing "ELO Balancer" functionality.

The button should attempt to improve the ELO balance by swapping players between teams.

However:

* Only perform legal swaps.
* A player's position assignment must remain valid after the swap.
* Do not swap players simply because it improves ELO if doing so substantially damages position preference satisfaction.
* Same-position swaps should remain the preferred mechanism where possible.

The algorithm should evaluate candidate swaps and select the best valid result.

## 8. Deterministic Behaviour

The matchmaking algorithm must be deterministic.

Given:

* the same players
* the same ELO ratings
* the same ranked position preferences
* the same match size

the algorithm should produce the same result.

Do not use an AI model, randomness, or nondeterministic behaviour during matchmaking.

This must be normal application code.

## 9. Edge Cases

Handle situations such as:

* Multiple players strongly preferring Setter.
* Only two players being capable of Setter.
* A specialist player competing with a flexible player for a position.
* Players with exactly 3 preferences.
* Players with 4 preferences.
* Players with all 5 preferences.
* A position having very few eligible players.
* Players having identical preference rankings.
* 12, 13 and 14 selected players.
* Very large ELO differences.
* Several equally good positional solutions.

The algorithm should fail gracefully if no valid assignment exists.

It should provide a useful error message explaining why a valid team composition could not be created rather than silently assigning invalid positions.
